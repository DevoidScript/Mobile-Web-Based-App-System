System Overview

Architecture

Smart Blood Management (Mobile/Web App) is a Progressive Web App (PWA) that provides a donor-facing platform for the Philippine Red Cross. The application is PHP-based with Supabase as the backend database. Donors can register, log in, track donations, view eligibility countdowns, and receive push notifications.

User Type

This application is designed for donors (no admin/hospital/staff roles). All authenticated users are donors who can:

  • Register and manage their profile
  • Start and track blood donation (parcel-style tracking)
  • View donation history and eligibility countdown
  • Subscribe to push notifications (blood drives, urgent requests)
  • Explore Red Cross resources and locations

Technology Stack

  • Backend: PHP 7.4+
  • Database: Supabase (PostgreSQL)
  • Frontend: HTML5, CSS3, vanilla JavaScript; mobile-first responsive design
  • PWA: Service worker, Web App Manifest, installable on mobile/desktop
  • Push: Web Push API, VAPID keys; subscription storage in Supabase
  • Email: PHPMailer for password reset and verification

Key Database Tables

donor_form - Donor registration and profile data donations - Blood donation records (per donation) donation_status_history - Status change history for parcel-style tracking users / donors_detail - Account and auth-related user data (project-specific) email_verifications - Email verification tokens push_subscriptions - Web Push subscription endpoints for notifications

API Endpoints Catalog

Authentication

POST api/auth.php?login

Purpose: User login (email/password).

Auth: None (public).

Request: POST body email, password.

Response: Redirect to dashboard on success; redirect to index with error on failure.

Used By: templates/login.php

POST api/auth.php?register

Purpose: User registration (donor account).

Auth: None (public).

Used By: templates/register.php

GET api/auth.php?logout

Purpose: Logout; destroy session and redirect.

Used By: Logout links across app

Donor & Donation

POST api/donor_register.php

Purpose: Register donor (donor_form and related data).

Auth: Session or public (project-specific).

Used By: templates/register.php, donor forms

GET / POST api/blood_tracker.php

Purpose: Donation tracker actions: get_tracker, start_donation, update_stage, get_status_history, auto_update_status.

Auth: Session required (is_logged_in()).

Params: action (get_tracker | start_donation | update_stage | get_status_history | auto_update_status); POST for update_stage.

Response: JSON (donation data, status history, or error).

Used By: templates/blood_donation.php, templates/blood_tracker.php, templates/dashboard.php

Push Notifications

Purpose: Save or update push subscription for logged-in donor.

Auth: Session required.

Request: JSON subscription object (endpoint, keys).

Response: { success, message, data }.

Used By: assets/js/push-notifications.js

GET api/get-notifications.php

Purpose: Fetch notifications for the bell panel (by donor_id from session).

Auth: Session required.

Params: Optional query params (limit, etc.).

Used By: Bell/notification UI in app

GET api/get-vapid-key.php

Purpose: Return public VAPID key for Web Push subscription.

Auth: Typically public or session.

Used By: Client push subscription flow

POST api/broadcast-blood-drive.php

Purpose: Send broadcast notification (blood drive, urgent request).

Auth: Admin or internal (project-specific).

Used By: templates/admin-send-notification.php

Push Notification Flow

1. User grants permission → Client subscribes (PushManager) → POST api/save-subscription.php 2. Subscription stored in push_subscriptions (donor_id, endpoint, keys) 3. Admin sends broadcast (api/broadcast-blood-drive.php) → Server sends Web Push to all subscriptions 4. Service worker receives push event → Shows notification; optional click to open app/page

Security Architecture & Considerations

This section summarizes authentication, access control, and security practices for the donor PWA.

1. Authentication & Session

  • Session-based auth: After login, $_SESSION['user'] holds user/donor data; pages check is_logged_in().
  • Password: Stored hashed (e.g. password_hash() / password_verify()); never stored plain.
  • Session regeneration: Used on sensitive pages (e.g. dashboard) to reduce fixation risk.

2. Access Control

  • Donor-only app: no role_id branching; authenticated users are donors.
  • Protected pages (dashboard, donation, tracker, profile, history) redirect to login if not authenticated.
  • APIs that handle donor data (e.g. blood_tracker, save-subscription, get-notifications) require is_logged_in().

3. Data Protection

  • Supabase: Use RLS where applicable; service role only where needed (e.g. donations, email_verifications).
  • Input: sanitize_input(), htmlspecialchars(), validation in includes/functions.php and APIs.
  • Config: Database and API keys in config/database.php; recommend moving secrets to environment variables in production.

4. Recommendations for Production

  1. CSRF: Add CSRF tokens to all state-changing forms (login, register, password reset, donation actions).
  2. HTTPS: Serve app and API over HTTPS only; required for PWA and Web Push.
  3. Secrets: Move Supabase keys, email credentials, and VAPID keys to .env and never commit them.
  4. Rate limiting: Apply to login, registration, and password-reset endpoints.
  5. Headers: Use security headers (CSP, X-Frame-Options, X-Content-Type-Options).
